copilot-instruction

Je veux construire un SaaS MVP de DCA crypto multi-utilisateur.

Objectif produit :
- L’utilisateur crée un compte
- Il souscrit à un abonnement mensuel via Stripe
- Il connecte son compte Binance avec une API key et un API secret
- Les secrets Binance ne doivent JAMAIS être stockés en clair dans Firestore
- Les secrets doivent être stockés dans Google Secret Manager
- L’utilisateur configure son DCA :
  - paire (liste fermée au début)
  - montant quotidien
  - heure d’exécution
  - notifications Telegram activées ou non
- Un scheduler backend exécute automatiquement les achats DCA pour chaque utilisateur actif
- Le backend vérifie toujours que l’abonnement Stripe est actif avant d’exécuter un achat
- L’utilisateur voit un dashboard Streamlit avec :
  - capital investi
  - quantité détenue
  - prix moyen
  - valeur actuelle
  - pnl valeur
  - pnl pourcentage
  - historique des achats
  - statut de l’abonnement
  - configuration DCA modifiable
- Chaque utilisateur ne doit voir QUE ses propres données
- Authentification via Firebase Auth
- Base applicative via Firestore
- Gestion des secrets via Google Secret Manager
- Paiement mensuel via Stripe subscriptions + webhooks
- Notifications achat/erreurs via Telegram bot unique avec chat_id par utilisateur
- Backend Python FastAPI
- Projet prêt pour déploiement sur VPS ou Google Cloud Run plus tard

Contraintes importantes :
- Ne jamais gérer l’argent des utilisateurs directement
- Les utilisateurs gardent leurs fonds sur leur propre compte Binance
- Les clés Binance doivent être trading only, sans retrait
- Séparer clairement backend, dashboard, scheduler et intégrations externes
- Prévoir logs, gestion des erreurs et audit minimal
- Prévoir architecture propre dès le départ, même si MVP
- Utiliser une whitelist de paires au début : BTCEUR, ETHEUR, BNBEUR, ADAEUR, SOLEUR
- Timezone par défaut : Europe/Paris

5. Secret Manager

Secret Manager est prévu pour stocker et gérer des secrets comme des API keys, mots de passe et certificats.

Règle

Ne jamais stocker api_key et api_secret Binance en clair dans Firestore.

Convention

Créer un secret par utilisateur :

binance-user-{uid}

Contenu JSON du secret :

{
  "api_key": "BINANCE_API_KEY",
  "api_secret": "BINANCE_API_SECRET"
}
Firestore stocke seulement la référence

Exemple :

{
  "secret_ref": "projects/my-project/secrets/binance-user-abc123/versions/latest"
}
Logique backend
création/rotation/suppression du secret via service dédié
lecture du secret uniquement au moment :
du test de connexion Binance
de l’exécution d’un ordre
d’une validation des permissions

9. Scheduler DCA
MVP

Utiliser un scheduler simple, une fois par minute.

À chaque cycle :

récupérer les utilisateurs actifs
vérifier abonnement
vérifier config DCA activée
vérifier si l’heure d’exécution correspond
récupérer clés Binance depuis Secret Manager
passer l’ordre
enregistrer l’ordre
recalculer snapshot
envoyer Telegram
Pseudocode
def run_dca_cycle():
    users = get_active_users()

    for user in users:
        if not is_subscription_active(user.uid):
            continue

        config = get_dca_config(user.uid)
        if not config or not config.enabled:
            continue

        if not should_run_now(config):
            continue

        if already_executed_today(user.uid, config.symbol):
            continue

        credentials = load_binance_credentials(user.uid)
        order = place_market_buy_order(
            api_key=credentials.api_key,
            api_secret=credentials.api_secret,
            symbol=config.symbol,
            quote_amount=config.daily_amount_eur,
        )

        save_order(user.uid, order)
        refresh_portfolio_snapshot(user.uid, config.symbol)

        if telegram_enabled(user.uid):
            send_order_notification(user.uid, order)
Verrous

Prévoir un verrou anti double exécution :

lock Firestore
ou idempotency key par uid + date + symbol

13. Firestore Security Rules minimales

Les Security Rules doivent empêcher un utilisateur de lire ou écrire les documents d’un autre utilisateur.

Exemple conceptuel :

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;

      match /{document=**} {
        allow read, write: if request.auth != null && request.auth.uid == userId;
      }
    }
  }
}

Important :

le frontend ne doit jamais pouvoir accéder aux secrets
Secret Manager reste côté backend uniquement
l’Admin SDK backend contourne les rules, donc toute logique serveur doit être propre et restrictive
